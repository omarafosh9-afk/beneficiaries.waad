# تصميم: قاعدة بيانات SQLite ونافذة مراجعة جهة العمل

- التاريخ: 2026-10-20
- الحالة: مسودة للمراجعة
- التصوّر المعتمد: https://claude.ai/artifact/7oAXDcVAsq1wAR6Fnhzy34 (الشاشة 1: جهة العمل)

## 1. الهدف

تحويل المنظومة من ملف `data/people.json` إلى قاعدة بيانات حقيقية، ثم بناء أول نافذة من المنظومة الجديدة: **نافذة مراجعة جهة العمل واعتمادها** كما في التصوّر المعتمد. هذه المرحلة هي الأساس الذي تُبنى عليه الحسابات والصلاحيات، وشاشة TPA للترحيل، والمطبعة، والاستلام.

## 2. ما اتُّفق عليه

- الأطراف: جهة العمل (حساب لكل جهة)، وشركة TPA (الإدارة)، والمطبعة.
- المسار: جهة العمل تتحقق وتعتمد ← TPA ترحّل للمطبعة ← المطبعة تطبع ← TPA تستلم وتتحقق.
- ترتيب الأعمدة: الرقم الوظيفي، اسم الموظف، اسم المستفيد، صلة القرابة، المواليد، رقم البطاقة.
- الحالات:

| الحالة | المعنى | من يضعها |
|---|---|---|
| بانتظار التحقق (`pending`) | لم تراجعه جهة العمل بعد | النظام |
| صحيح (`correct`) | جهة العمل أكدت البيانات كما هي | جهة العمل |
| معدل (`modified`) | جهة العمل عدّلت بيانات مع ذكر السبب | جهة العمل |
| يحتاج تعديل (`needs_edit`) | TPA أعادته لجهة العمل مع ملاحظة | TPA |
| مرحّل (`forwarded`) | أُرسل للمطبعة ضمن دفعة، ويُقفل | TPA |
| مطبوع (`printed`) | المطبعة أكدت الطباعة | المطبعة |
| مُسلَّم (`delivered`) | استُلمت البطاقة وتحقق منها | TPA |

## 3. النطاق

### داخل هذه المرحلة
1. قاعدة بيانات SQLite بجداولها، وترحيل كل البيانات الحالية إليها.
2. تحويل الميزات الحالية (البحث، الإضافة، التعديل، الحذف والاستعادة، الاستيراد، التصدير) لتقرأ وتكتب من القاعدة، فيبقى مصدر واحد للبيانات.
3. نافذة المراجعة `/review` بكل سلوك الشاشة 1 في التصوّر.
4. سجل تغييرات لكل اعتماد وتعديل.
5. أمر للنسخ الاحتياطي.

### خارج هذه المرحلة (مراحل لاحقة)
- **المرحلة 2:** الحسابات وتسجيل الدخول والصلاحيات، والنشر على الإنترنت. حتى ذلك الحين تعمل المنظومة على جهاز TPA فقط، ويُسجَّل الفاعل في السجل باسم «محلي».
- **المرحلة 3:** شاشة TPA (الإعادة للتعديل، ودفعات الطباعة، والترحيل)، وشاشة المطبعة.
- **المرحلة 4:** الاستلام والتحقق وإعادة الطباعة.

في هذه المرحلة لا يوجد زر يضع الحالة «يحتاج تعديل»، لأنه زر TPA ويأتي مع شاشتها. القاعدة تدعم الحالة، وتعرضها النافذة إن وُجدت.

## 4. قرار قاعدة البيانات

**التوصية: SQLite عبر الوحدة المدمجة في Node.js (`node:sqlite`).**

لماذا:
- **الحجم صغير عليها:** في القاعدة الحالية 17,723 سجلًا نشطًا (الاسمنت 1,297، جليانة 6,545، الجمارك 9,881). SQLite تتعامل بسهولة مع ملايين السجلات.
- **بلا خادم ولا تثبيت:** ملف واحد `data/app.db`. لا خدمة تُثبَّت أو تُدار على Windows.
- **بلا مكتبات خارجية:** `node:sqlite` مدمجة في Node 25.9 المثبّت (SQLite 3.51.3، تم التحقق). هذا يتجنب مشاكل تجميع المكتبات الأصلية على Windows، مثل `better-sqlite3`. ووثائق Next.js 16 المرفقة بالمشروع تذكرها صراحة كمشغّل مدعوم.
- **أمان الكتابة المتزامنة:** معاملات (transactions) ووضع WAL، بدل إعادة كتابة ملف JSON كاملًا مع كل تعديل. وقد ظهر خطأ قفل في `people.json` أثناء العمل سابقًا.
- **نسخ احتياطي بسيط:** نسخة متسقة بأمر واحد (`VACUUM INTO`).

البدائل:
- **PostgreSQL:** الأنسب إذا استُضيفت المنظومة على عدة خوادم أو خدمة سحابية مُدارة. تكلفته الآن: خادم يُثبَّت ويُدار ويُنسخ احتياطيًا. ننتقل إليه عند الحاجة، ويسهّل ذلك أن الوصول للبيانات محصور في طبقة واحدة (`lib/`) بلغة SQL قياسية.
- **SQL Server / MySQL:** نفس تكلفة PostgreSQL، بلا ميزة إضافية لهذا الحجم.
- **ORM مثل Prisma:** طبقة توليد وإعدادات إضافية لا يحتاجها مشروع بهذا الحجم مكتوب بـ JavaScript.

## 5. نموذج البيانات

```sql
PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;

CREATE TABLE entities (
  id          INTEGER PRIMARY KEY,
  code        TEXT NOT NULL UNIQUE,   -- Cement | Jalyana | Jamarek (نفس أسماء مجلدات الصور)
  name_ar     TEXT NOT NULL,          -- الاسمنت | جليانة | الجمارك
  card_prefix TEXT NOT NULL           -- LCC | JFZ | JMR
);

CREATE TABLE beneficiaries (
  id              INTEGER PRIMARY KEY,           -- نفس المعرّفات الحالية في people.json
  entity_id       INTEGER NOT NULL REFERENCES entities(id),
  family_key      TEXT NOT NULL,                 -- مفتاح العائلة المشتق من رقم البطاقة
  job_no          TEXT,                          -- الرقم الوظيفي
  employee_name   TEXT,                          -- اسم الموظف (رب العائلة)
  name            TEXT NOT NULL,                 -- اسم المستفيد
  relation        TEXT NOT NULL,
  dob             TEXT,                          -- YYYY-MM-DD أو YYYY (سنة فقط) أو NULL
  national_id     TEXT,
  card1           TEXT,
  card2           TEXT,
  photo_file      TEXT,                          -- اسم ملف الصورة داخل public/storage/<code>/ ، NULL = بلا صورة
  review_status   TEXT NOT NULL DEFAULT 'pending'
                  CHECK (review_status IN ('pending','correct','modified','needs_edit','forwarded','printed','delivered')),
  review_note     TEXT,                          -- ملاحظة TPA مع «يحتاج تعديل»
  modified_reason TEXT,                          -- آخر سبب تعديل من جهة العمل
  intake_batch    INTEGER,                       -- دفعة قائمة جهة العمل (مثل الدفعة الأولى 2027)
  legacy_status   TEXT,                          -- نشط / موقوف / مكتمل من البيانات الأصلية
  deleted         INTEGER NOT NULL DEFAULT 0,
  search_key      TEXT NOT NULL,                 -- نص بحث مُطبَّع (الاسم، الموظف، الرقم الوظيفي، البطاقتان، الرقم الوطني)
  version         INTEGER NOT NULL DEFAULT 1,    -- يزيد مع كل تعديل لكشف التعديل المتزامن
  updated_at      TEXT NOT NULL
);
CREATE INDEX idx_benef_entity_status ON beneficiaries(entity_id, deleted, review_status);
CREATE INDEX idx_benef_entity_family ON beneficiaries(entity_id, family_key);
CREATE INDEX idx_benef_card1 ON beneficiaries(card1);
CREATE INDEX idx_benef_card2 ON beneficiaries(card2);

CREATE TABLE beneficiary_events (                -- سجل التغييرات
  id             INTEGER PRIMARY KEY,
  beneficiary_id INTEGER NOT NULL REFERENCES beneficiaries(id),
  action         TEXT NOT NULL,   -- approve | edit | photo | add | delete | restore | import
  field          TEXT,            -- الحقل المعدل في action = edit
  old_value      TEXT,
  new_value      TEXT,
  reason         TEXT,
  actor          TEXT NOT NULL,   -- «محلي» حتى تأتي الحسابات في المرحلة 2
  at             TEXT NOT NULL    -- ISO 8601
);
CREATE INDEX idx_events_benef ON beneficiary_events(beneficiary_id, id);
```

- **نسخة المخطط:** تُحفظ في `PRAGMA user_version`. كل تغيير لاحق في المخطط ملف SQL مرقّم في `db/migrations/` يُطبَّق تلقائيًا عند فتح القاعدة.
- **القيمة القديمة («كان: …»):** تُقرأ من سجل التغييرات، وهي `old_value` في أول حدث `edit` لكل حقل.
- **الصور:** تبقى في `public/storage/<code>/` كما هي الآن. القاعدة تحفظ اسم الملف فقط، فلا يلزم إعادة تسمية الصورة عند تعديل الاسم. الصورة الجديدة تُحفظ باسم `<id>.webp`.

### قواعد الاشتقاق عند الترحيل

| الحقل | القاعدة |
|---|---|
| `family_key` | من `card1` (أو `card2` إن كان الأول فارغًا) بالنمط `^(LCC\|JFZ\|JMR)2025(VIP)?0*(\d+)`: الأرقام بلا أصفار بادئة، وتسبقها `VIP` إن وُجدت. إن لم يطابق: `id:<id>`، أي عائلة من فرد واحد. |
| `job_no` | جليانة والجمارك: أرقام `family_key` (طابقت قوائم الجهات في 3,400 من 3,416 حالة في الجمارك و195 من 203 عائلات في جليانة). الاسمنت: حقل `job` للسجل نفسه، وإلا حقل `job` لرب العائلة. |
| `employee_name` | `primaryName` إن وُجد، وإلا اسم رب العائلة (صلة «موظف أساسي» أو «موظف» في نفس الجهة والعائلة). ولرب العائلة نفسه: اسمه. |
| `photo_file` | `<photoSlug>.webp` إن كان الملف موجودًا فعلًا، وإلا NULL. |
| `review_status` | `pending` لكل السجلات. |
| `intake_batch` | من الحقل `batch` الحالي (993 سجلًا في جليانة للدفعة الأولى). |
| `legacy_status`, `national_id`, `card1`, `card2`, `dob`, `deleted` | تُنقل كما هي. |

### قواعد الانتقال بين الحالات (هذه المرحلة)

| العملية | من | إلى | الشرط |
|---|---|---|---|
| اعتماد (سجل، عائلة، تحديد، أو كل المطابق للفلتر) | `pending` | `correct` | — |
| تعديل | `pending`, `correct`, `modified`, `needs_edit` | `modified` | سبب إلزامي، وتغيير فعلي في حقل أو صورة |
| أي عملية | `forwarded`, `printed`, `delivered` | — | مقفلة |

- `needs_edit` لا يُعتمد مباشرة؛ يُعدَّل أولًا.
- الاعتماد على `correct` أو `modified` لا يغيّر شيئًا، ويُذكر في نافذة التأكيد كـ«بلا تغيير».

## 6. ترحيل البيانات الحالية

- أمر `npm run db:import` (سكربت `scripts/db-import.mjs`):
  - ينشئ `data/app.db` من `data/people.json` بقواعد الاشتقاق أعلاه، في معاملة واحدة.
  - يرفض العمل إن كانت القاعدة موجودة وفيها أحداث مراجعة، إلا مع `--force`، حتى لا يمسح عملًا مُنجزًا.
  - يطبع ملخصًا للتحقق.
- **الأرقام المتوقعة:** 1,297 / 6,545 / 9,881 سجلًا نشطًا، و16 محذوفًا. سجلات بصور: 471 / 1,269 / 7,904. وعدد `intake_batch = 1`: 993.
- يبقى `people.json` بلا تعديل كنسخة احتياطية للقراءة فقط. بعد الترحيل لا تكتب المنظومة فيه.
- أمر `npm run db:backup`: ينسخ القاعدة بأمان إلى `data/backups/app-YYYYMMDD-HHmm.db`.

## 7. نافذة المراجعة `/review`

مطابقة للشاشة 1 في التصوّر المعتمد.

### المكونات
- **رأس الصفحة:** العنوان، ومُختار جهة العمل (الاسمنت / جليانة / الجمارك). في أول زيارة تُختار أول جهة في القائمة، ثم يُحفظ آخر اختيار في المتصفح. في المرحلة 2 يُستبدل المُختار بجهة المستخدم المسجّل.
- **تقدّم المراجعة:** «تمت مراجعة X من Y» مع شريط. المراجَع هو كل ما ليس `pending` أو `needs_edit`، محسوبًا على كل سجلات الجهة.
- **تبويبات الحالات بعدّاداتها:** الكل، بانتظار التحقق، يحتاج تعديل، صحيح، معدل، مرحّل. العدّادات تحترم البحث والفلاتر الأخرى.
- **شريط الأدوات:**
  - بحث بالاسم أو الرقم الوظيفي أو رقم البطاقة، مع تطبيع عربي (أ/إ/آ ← ا، ى ← ي، ة ← ه، وحذف التشكيل).
  - فلتر صلة القرابة.
  - فلتر اكتمال البيانات: مكتملة، أو ناقصة (بلا صورة أو بلا مواليد).
  - فلتر دفعة القائمة: يظهر فقط إن كان للجهة سجلات لها `intake_batch`.
  - مفتاح «تجميع حسب العائلة».
  - التبديل بين الجدول والكروت.
  - زر التصدير.
  - زر «اعتماد المحدد (n)».
- **الجدول المجمّع:**
  - صف عنوان لكل عائلة: الرقم الوظيفي، اسم الموظف، عدد الأفراد، ملخص الحالات، وزر «اعتماد العائلة».
  - تحته صفوف الأفراد: الصورة، اسم المستفيد، صلة القرابة، المواليد، رقم البطاقة، الحالة، الإجراءات.
  - ترتيب الأفراد: موظف، زوج أو زوجة، أبناء، أب، أم.
- **الجدول غير المجمّع:** نفس أعمدة التصوّر الأصلي بالترتيب المطلوب.
- **عرض الكروت:** بطاقة لكل مستفيد فيها صورة أكبر، والاسم، وصلة القرابة والمواليد، ورقم البطاقة، والرقم الوظيفي، والحالة، والإجراءات نفسها.
- **داخل الصف:**
  - السجل المعدل يعرض القيمة الجديدة بلون مميز، وتحتها «كان: …» وسبب التعديل.
  - السجل «يحتاج تعديل» يعرض ملاحظة TPA.
  - النقص يظهر في مكانه: «بلا صورة» أو «ناقص» في المواليد. والمواليد التي هي سنة فقط تُعلَّم «سنة فقط».
- **الإجراءات:**
  - «صحيح»: يظهر للحالة `pending` فقط.
  - «تعديل»: يظهر لكل ما ليس مقفلًا.
  - «مقفل بعد الترحيل»: للحالات المقفلة.
- **التحديد:**
  - مربع لكل صف، ولكل عائلة، ولكل الظاهر.
  - عند تحديد كل الظاهر يظهر شريط «تحديد كل السجلات المطابقة للفلتر»، فيُنفَّذ الاعتماد على الخادم حسب الفلتر نفسه.
- **نافذة تأكيد الاعتماد:** تعرض ثلاثة أعداد يحسبها الخادم: ما سيُعتمد، وما لن يُعتمد لأنه «يحتاج تعديل»، وما سيبقى بلا تغيير.
- **لوحة التعديل:**
  - الحقول: الاسم، صلة القرابة، المواليد، ورفع صورة أو استبدالها.
  - الرقم الوظيفي ورقم البطاقة للعرض فقط.
  - سبب التعديل إلزامي.
  - تُعرض ملاحظة TPA إن وُجدت.
- **التصفح بالصفحات:**
  - في العرض المجمّع: 20 عائلة لكل صفحة، فلا تنقسم عائلة بين صفحتين.
  - في العرض غير المجمّع: 50 سجلًا لكل صفحة.
  - ترتيب العائلات تصاعديًا بالرقم الوظيفي.
- **التصدير:** ملف Excel لكل ما يطابق الفلتر الحالي. الأعمدة: الرقم الوظيفي، اسم الموظف، اسم المستفيد، صلة القرابة، المواليد، رقم البطاقة، الحالة، سبب التعديل.
- **التنقل:**
  - الصفحة الرئيسية الحالية تبقى كما هي (البحث والصور)، ويضاف فيها رابط «مراجعة واعتماد المستفيدين».
  - نافذة المراجعة فيها رابط للعودة.

### الواجهات الخلفية
- **القراءة:** `GET /api/review` بالمعاملات `entity, tab, q, relation, completeness, intake, grouped, page`. يعيد العدّادات، والتقدّم، وصفحة العائلات أو السجلات، والقيم القديمة للسجلات المعدلة. استعلامان: الأول يجلب مفاتيح عائلات الصفحة، والثاني يجلب أفرادها. البحث بمطابقة جزئية (`LIKE`) على `search_key` بعد تطبيع نص البحث بنفس الطريقة.
- **التعديلات (Server Actions في `app/review/actions.js`):**
  - `previewApproval(target)`: يحسب أعداد نافذة التأكيد.
  - `approve(target)`: الهدف إما قائمة معرّفات، أو مفتاح عائلة، أو الفلتر نفسه.
  - `editBeneficiary(formData)`: يتضمن `id` و`version` والحقول والسبب والصورة.
  - كل عملية في معاملة واحدة، وتكتب أحداثها في السجل.
- القراءة تتم وقت الطلب في Route Handler وServer Actions. وإن قُرئت القاعدة يومًا داخل Server Component فيُستدعى `connection()` قبل الاستعلام، كما توصي وثائق Next.js 16 للمشغّلات المتزامنة.

## 8. تحويل الميزات الحالية إلى القاعدة

- **الطبقة الجديدة:**
  - `lib/db.js`: الاتصال (مرة واحدة لكل عملية، ومحفوظ على `globalThis` في وضع التطوير)، وإعدادات WAL، وتطبيق المخطط.
  - `lib/beneficiaries.js`: كل الاستعلامات والكتابة.
  - `lib/normalize.js`: التطبيع العربي المستخدم في البحث.
- **الملفات التي تتحول للقراءة والكتابة من القاعدة:** `app/api/search/route.js`، و`app/actions.js` (التعديل والإضافة والحذف والاستعادة والاستيراد والإضافة القسرية)، و`app/api/bulk-delete`، و`app/api/export-zip`، و`app/api/import-report-export`.
- **شكل البيانات:** دالة `listForLegacy()` تعيد السجلات بنفس الشكل الذي تتوقعه الشاشات الحالية. فلاتر البحث الخاصة الحالية (المكرر، وبلا زوج أو زوجة، والدفعة الأولى) تبقى بنفس منطقها. الصورة تُعرض من `photo_file` بدل `photoSlug`.
- **رفع الصور في الشاشة الحالية:** يُحفظ الملف باسم `<id>.webp` ويُحدَّث `photo_file`، بدل التسمية بالاسم ورقم البطاقة. لذلك لم يعد تعديل الاسم يتطلب إعادة تسمية ملف الصورة.
- **سجل التغييرات:** التعديل والإضافة والحذف والاستعادة والاستيراد في الشاشة الحالية تُسجَّل أيضًا في `beneficiary_events`.
- **السكربتات القديمة** في `scripts/` تعمل على `people.json`، وتبقى للرجوع فقط. أي ربط صور جديد سيُكتب لاحقًا ليستهدف القاعدة.

## 9. الأمان والخصوصية في هذه المرحلة

- **لا حسابات بعد:** المنظومة تعمل على جهاز TPA أو الشبكة الداخلية فقط، ولا تُنشر على الإنترنت قبل المرحلة 2.
- **حماية البيانات الشخصية من git:** يُضاف إلى `.gitignore` كل من `/data/` و`/public/storage/`، قبل أي commit. البيانات الشخصية والصور لا تدخل git أبدًا.
- **مدخلات لوحة التعديل تُتحقق على الخادم:**
  - الاسم غير فارغ وحتى 120 حرفًا.
  - صلة القرابة من قائمة ثابتة.
  - المواليد بالصيغة YYYY أو YYYY/MM/DD أو YYYY-MM-DD، تاريخ حقيقي بين 1900 واليوم.
  - السبب حتى 300 حرف.
  - الصورة JPG أو PNG أو WebP حتى 10 ميغابايت، وتُحوَّل إلى WebP بعرض 500 بكسل كما الآن.

## 10. الأخطاء والحالات الحدّية

- **تعديل متزامن:** إن تغيّر `version` منذ فتح لوحة التعديل، يُرفض الحفظ برسالة «عُدّل هذا السجل للتو من مكان آخر؛ حدّث الصفحة». ولا يُكتب شيء.
- **اعتماد يشمل سجلات مقفلة أو «يحتاج تعديل»:** تُتخطى، وتظهر أعدادها في النتيجة.
- **القاعدة مشغولة:** انتظار حتى 5 ثوانٍ (`busy_timeout`)، ثم رسالة خطأ واضحة دون فقدان بيانات.
- **فشل حفظ الصورة:** تُلغى المعاملة كاملة، فلا يُسجَّل تعديل ناقص.
- **القاعدة غير موجودة:** رسالة توجّه لتشغيل `npm run db:import`.

## 11. الاختبار

- **أداة الاختبار:** `node --test` المدمجة، بلا مكتبات جديدة. كل اختبار على قاعدة مؤقتة.
- **الاختبارات:**
  - **قواعد الاشتقاق:** مفتاح العائلة (ومنه حالات VIP والبطاقات الشاذة)، والرقم الوظيفي (ومنه رب العائلة في الاسمنت)، واسم الموظف عند غياب `primaryName`.
  - **قواعد الحالات:** اعتماد `pending` فقط، ورفض اعتماد `needs_edit`، وقفل الحالات المرحّلة، والتعديل يتطلب سببًا وتغييرًا فعليًا، وكشف التعديل المتزامن.
  - **الترحيل:** ملف `people.json` صغير للاختبار يتحقق من الأعداد، والمحذوفين، والصور الموجودة فعلًا، و`intake_batch`.
  - **الاستعلامات:** تصفح العائلات دون تقسيمها، والعدّادات مع الفلاتر، والتطبيع العربي في البحث، والقيم القديمة من السجل.
- **على البيانات الحقيقية:** تشغيل `db:import` ومطابقة الأرقام المتوقعة في القسم 6.
- **يدويًا:** تشغيل `npm run dev` وتجربة الاعتماد (فردي، وعائلة، وتحديد، وكل المطابق)، والتعديل مع صورة، والفلاتر، والتصدير. ثم التأكد أن الشاشة الحالية (البحث والإضافة والاستيراد) ما زالت تعمل.

## 12. ترتيب التنفيذ المقترح

0. **الأمان:**
   - إضافة `/data/` و`/public/storage/` إلى `.gitignore`.
   - إنشاء فرع `feature/review-db`.
   - commit أساسي للكود الحالي، بدون بيانات أو صور، ومعه هذه الوثيقة.
1. **طبقة القاعدة:** المخطط، والترحيل، والنسخ الاحتياطي، واختباراتها.
2. **تحويل الميزات الحالية إلى القاعدة**، والتحقق من الشاشة الحالية.
3. **واجهات نافذة المراجعة الخلفية** واختباراتها.
4. **واجهة `/review`** حسب التصوّر.
5. **التحقق على البيانات الحقيقية**، وأخذ نسخة احتياطية.

## 13. افتراضات للمراجعة

- **عدد المستفيدين:** ذُكر 12,000، والقاعدة الحالية فيها 17,723 سجلًا نشطًا. التصميم يعمل للعددين.
- **حالة البداية:** كل السجلات تبدأ «بانتظار التحقق»، ومنها سجلات الدفعة الأولى لجليانة.
- **الرقم الوظيفي:** جهة العمل لا تعدّله في هذه النافذة. تصحيحه يتم من شاشة البحث الحالية بواسطة TPA.
- **القيمة القديمة:** «كان: …» تعرض القيمة قبل أول تعديل. دورات المراجعة السنوية (2027، 2028…) تُصمَّم مع المرحلة 3.
